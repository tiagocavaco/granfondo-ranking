# Feature specs — project-level additions (19 Sep 2026)

Seven items raised after the main plans were written. The first is a
safeguard, not a feature, and belongs in Milestone 0.

## 1. Override backup and key custody (Milestone 0)

**Context:** the owner keeps a copy of the repository folder outside the
repo. That covers losing the file, if the copy includes `scraper/.env`. The
export below adds what a copy cannot: a readable diff, so a bad state is
noticed before it is backed up over a good one.

**Problem:** the four manual override tables (athlete alias rules, result
assignments, blocked results, team aliases) exist only inside
`frontend/public/data/data.db.enc`. They are the product of months of
human judgement and cannot be regenerated. A lost key, a corrupted file, or
a rebase that keeps `--ours` erases them. Everything else in the DB can be
re-scraped.

**Do:**
- At the end of every scrape and every backoffice write, export the four
  tables to `scraper/overrides.json` (committed). Names in it are the same
  names already on the public site; no licences, no emails.
- On scraper start, if the DB has fewer override rows than the file, stop
  with an error naming the difference (guards against the rebase case).
- `npm run db:restore-overrides` re-imports the file into a DB.
- Store `DATA_KEY` and the CI `PAT` in a password manager vault shared with
  one trusted second person; write the rotation steps in the runbook.

**Acceptance:** deleting `data.db.enc`, regenerating with `scrape:force`,
and running `db:restore-overrides` yields the same `db:manage -- list`.

## 2. Organiser results upload

**What:** a cooperating organiser (or timing company) uploads the official
results CSV instead of being scraped. Backoffice page or a signed upload
URL per event; mapped to a registry event with `results.source: upload`.

**Why:** removes layout-drift risk for the organisers that run half the
calendar; a tangible benefit in the organiser package.

**Method:** accept CSV with a column-mapping step (bib, name, team,
category, gender, time, status); validate against the start list; write
into the same `StoredEventResults` shape the adapters produce; keep the
uploaded file as the audit source.

**Acceptance:** an uploaded event goes through the identity pipeline
identically to a scraped one; the uploader sees the parsed row count and
any rejected rows before confirming.

## 3. Data artefacts outside the code repository's history

**What:** publish `data.db.enc` (and the v2 artefacts) as a GitHub Release
asset or to R2, not as commits. The deploy job fetches by hash from the
manifest.

**Why:** each bot commit adds ~49 MB to history; clones and CI slow down;
code review is interleaved with data commits; the destructive
history-cleanup workflow exists because of this.

**Method:** the scrape workflow uploads artefacts and commits only
`manifest.json` and `scraped-events.json`; the deploy reads the manifest
and pulls the artefacts into `frontend/public/data/` at build time.
Backoffice and scraper read from the same source via a small `fetchArtefact`
helper with a local cache. Do this together with
`docs/specs/data-artefacts.md`.

**Acceptance:** `git clone --depth 1` under 20 MB; a data refresh produces
a one-line diff in git.

## 4. "Report an error" on athlete pages

**What:** a link on every athlete profile and result row that opens a
prefilled form or `mailto:` with the page URL and the result identifier.
Submissions land in the review queue as source `rider-report`.

**Why:** it is the working form of the right to object in the privacy
notice, and riders are the best detectors of merged profiles.

**Method:** until the backend exists, `mailto:` with subject
`[report] athlete <id> event <id>`; after it exists, `POST /reports` with
optional email for follow-up; the queue item's suggested action is
"split" when the report says "not me".

**Acceptance:** every report becomes a queue item within one scrape cycle;
the reporter gets a reply within 30 days (privacy notice promise).

## 5. Large-text mode for the 60+ field

**What:** a "Texto grande" toggle that raises the base size one step and
the informational minimum to 15 px; persisted in `localStorage`.

**Why:** Masters D and E riders are a meaningful share of finishers; the
site's small eyebrow type and dark theme are hardest on them.

**Method:** a `data-text="large"` attribute on `<html>` that the type
tokens respond to (`docs/specs/design-system.md` §2). Zero cost once
tokens exist; also improves the audit's tiny-text count.

**Acceptance:** with the toggle on, no informational text under 15 px on
any route.

## 6. Automated content channel

**What:** an Instagram (and optionally Facebook) account that posts the
favourites image 48 hours before each race and the podiums image after
results land, generated by the share-card renderer; a monthly newsletter
later.

**Why:** the site has no distribution; the predictions and podium images
are already the deliverable organisers pay for, so the marginal cost is a
posting job.

**Method:** cron after the participants refresh and after a results
commit; images from the share-card endpoint; captions from a template with
event name, date, distances, link. Use the platform's official API or a
scheduling service; never scrape or automate a personal account.

**Acceptance:** two posts per race with zero manual steps; link clicks
visible in analytics.

## 7. Season-end recognition

**What:** a "Campeão da série" per distance and gender, and per category,
announced on the site at season end with a share card; optionally a
modest sponsored prize presented at the last race with the organiser.

**Why:** gives the ranking a purpose riders feel; gives a sponsor a moment;
gives organisers a reason to link.

**Method:** a `/season/:year` page listing champions and podiums per slice,
generated from `aggregate_athletes` after the final event (registry marks
the last event of a season); cards per champion; email to claimed
champions.

**Acceptance:** page exists for 2023–2026 retroactively; champions match
the ranking's rank 1 per slice.
